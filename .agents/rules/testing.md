# テストルール

## 基本方針

- テストは**動作仕様のドキュメント**として扱う — テストを読めば仕様が分かるように書く
- **テスト戦略・カバレッジ基準はプロジェクト開始時に決定する**（後述の「プロジェクト定義事項」を参照）
- テストコードも本番コードと同等の品質基準で書く
- テストは**決定的（Deterministic）**であること — 何度実行しても同じ結果になること

---

## テストの種類と方針

### ユニットテスト

- **対象**: 単一の関数・クラス・モジュール
- **方針**: 外部依存（DB・API・ファイルシステム等）はモック/スタブに置き換える
- **粒度**: 1つのテストケースは1つの振る舞いのみを検証する
- DDDのdomain層はユニットテストを**必須**とする

### 統合テスト

- **対象**: 複数のモジュールが連携する境界（DB・外部API・メッセージキュー等）
- **方針**: 実際のインフラコンポーネント（またはテスト用の実物相当品）を使う
- モックで隠蔽しすぎない — 統合テストでモックを使うと結合の問題を見逃す
- DDDのinfrastructure層は統合テストを**必須**とする

### E2Eテスト

- **対象**: ユーザー視点のユースケース全体のフロー
- **方針**: クリティカルパス（主要なユースケース）のみを対象とする
- E2Eの数は最小限に抑え、ユニット・統合テストで担保できるものは下位レイヤーに委ねる

---

## テストピラミッド

```
        /\
       /E2E\        ← 少数・クリティカルパスのみ
      /------\
     / 統合   \     ← 境界・インフラ層
    /----------\
   /  ユニット  \   ← 多数・ドメイン・アプリケーション層
  /--------------\
```

ピラミッドの逆転（E2Eが多くユニットが少ない構成）は禁止する。

---

## テストの書き方

### 命名規則

- テスト名は **「状況 → 操作 → 期待結果」** の形式で書く
  ```
  // 例
  "有効なメールアドレスで登録したとき、ユーザーが作成されること"
  "残高が不足しているとき、支払いが失敗すること"
  ```
- テスト名から何を検証しているか一目で分かるようにする

### 構造（AAA パターン）

テストは以下の3セクションで構成する：

```
Arrange（準備）  — テスト対象の状態・入力データを用意する
Act（実行）      — テスト対象の処理を1つだけ実行する
Assert（検証）   — 期待する結果を検証する
```

### 1テスト1アサーション原則

- 1つのテストで検証する振る舞いは1つに絞る
- 複数のアサーションが必要な場合は、それが本当に1つの振る舞いか再考する

---

## モック・スタブの指針

- **モックは外部境界にのみ使う** — DB、外部API、時刻、乱数など
- ドメインロジック内部のモックは避ける（設計の問題を隠蔽する）
- テスト用のフェイク実装（インメモリDB等）はモックより優先して使う
- モックの検証は「呼ばれたか」よりも「何を返したか」に集中する

---

## テストデータ

- テストデータは**テストケース内で完結**させる — 共有の外部ファイルや共有状態に依存しない
- ファクトリ関数やビルダーパターンでテストデータを生成する
- 本番データをテストに使用しない
- エッジケース（空・null・境界値・最大値）を必ずテストする

---

## カバレッジ

- カバレッジ基準は**プロジェクト定義事項**として決定する（推奨: ライン・ブランチとも90%以上）
- カバレッジが低い箇所はレビュー時に指摘する
- 以下はカバレッジ対象から除外してよい
  - 自動生成コード
  - 設定ファイル・定数定義
  - 薄いDTOクラス

---

## プロジェクト定義事項

以下はプロジェクト開始時にチームで決定し、プロジェクトの `CLAUDE.md` または `docs/testing-policy.md` に記載する。

| 項目 | 決定すべき内容 | 推奨デフォルト |
|---|---|---|
| カバレッジ基準 | ライン・ブランチの最低ライン | 90% 以上 |
| テスト対象範囲 | ユニット・統合・E2E のどこまで実施するか | テストピラミッド準拠 |
| モック戦略 | 外部依存をどこまでモックするか | 外部境界のみ |
| テスト実行タイミング | CI でのテスト実行方針（PR時・マージ後など） | PR時に全テスト実行 |
| E2Eの対象フロー | クリティカルパスをどのユースケースにするか | プロジェクトごとに列挙 |

> **注意**: 決定していない項目はこのファイルのデフォルト方針に従う。

---

## 禁止事項

- テストが他のテストの実行順序に依存する実装（テスト間の状態共有）
- `sleep` や `wait` による時間依存テスト — タイムアウトや非同期処理は適切な仕組みで制御する
- 本番コードにテスト用の分岐（`if (isTest) {...}`）を埋め込む
- テストを通過させるためだけのコードを本番に追加する
- コメントアウトされたテストをリポジトリに残す（削除かスキップ記法を使う）
