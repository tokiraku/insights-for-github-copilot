# 要件からタスク生成スキル

## 概要

`/requirements` または `/tech-requirements` スキルで作成した要件ドキュメントを読み込み、
実装可能な粒度のタスクに分解して以下の2箇所に出力する：

1. **`tasks/todo.md`** — セッションをまたいで参照できる永続的なタスクリスト
2. **TodoWrite** — 現セッションのタスク管理にセット

---

## 実行手順

### Step 1: 要件ドキュメントの特定

引数としてファイルパスが渡された場合はそれを使用する。
渡されていない場合は以下の順で自動検索する：

1. `docs/requirements/` 配下の `*.md` を Glob で一覧取得
2. ファイルが複数ある場合は一覧をユーザーに提示し、対象を AskUserQuestion で確認する
3. ファイルが1つだけの場合はそのまま使用する
4. ファイルが存在しない場合は「要件ドキュメントが見つかりません。`/requirements` または `/tech-requirements` を先に実行してください」とメッセージを出して終了する

対象ファイルが確定したら全ファイルを Read で読み込む。
`*-tech-requirements.md` と機能要件 `*-requirements.md` が両方ある場合は両方読み込む。

---

### Step 2: 要件の解析

読み込んだドキュメントから以下を抽出する：

**機能要件 (FR-xxx) から抽出するもの：**
- 要件ID・要件名・優先度（MoSCoW）・受け入れ基準（Given/When/Then）

**非機能要件 (NFR-xxx) から抽出するもの：**
- 要件ID・カテゴリ（パフォーマンス/セキュリティ/可用性等）・計測基準

**技術要件ドキュメントから追加で抽出するもの：**
- 技術スタック（フロントエンド・バックエンド・DB・インフラ）
- マイルストーン・フェーズ情報
- アーキテクチャ制約（CON-xxx）

---

### Step 3: タスクへの分解

#### 分解の粒度

タスクは **実装レベル** の粒度で定義する。

| 粒度の基準 | 良い例 | 悪い例（粗すぎ）|
|-----------|--------|----------------|
| 単一の実装単位 | `JWTトークン検証ロジックを実装する` | `認証機能を実装する` |
| 1〜2時間で完了できる規模 | `ユーザーテーブルのマイグレーションを作成する` | `DBを設計する` |
| 完了が明確に判断できる | `POST /auth/login エンドポイントを実装する` | `ログインAPIを作る` |

#### フェーズ分類

タスクは以下のフェーズに分類する：

```
フェーズ1: 設計・準備
  - アーキテクチャ設計・ER図作成・API設計・環境構築

フェーズ2: インフラ・基盤
  - DBマイグレーション・認証基盤・共通ミドルウェア・ルーティング設定

フェーズ3: ドメイン層 (Must Have 優先)
  - エンティティ・値オブジェクト・ドメインサービス・リポジトリインターフェース

フェーズ4: アプリケーション層
  - ユースケース・DTOの組み立て・トランザクション管理

フェーズ5: プレゼンテーション層
  - APIエンドポイント・バリデーション・レスポンス変換

フェーズ6: フロントエンド（フルスタックの場合）
  - コンポーネント・APIクライアント・状態管理

フェーズ7: テスト
  - ユニットテスト（domain層）・統合テスト（infrastructure層）・E2Eテスト

フェーズ8: 非機能要件対応
  - パフォーマンスチューニング・セキュリティ対応・ロギング・監視設定
```

#### タスクIDの命名規則

- 要件IDを引き継ぐ: `FR-001-01`, `FR-001-02`（同一要件から複数タスクが生まれる場合は枝番）
- インフラ・設計タスクは `INFRA-001`, `SETUP-001` 等の独自プレフィックスを使う
- テストタスクは元タスクIDに `-test` を付ける: `FR-001-01-test`

---

### Step 4: ユーザーへのタスク一覧提示・確認

タスク一覧を以下の形式でユーザーに提示し、承認を求める：

```
## 生成予定のタスク一覧

### フェーズ1: 設計・準備
- [ ] [SETUP-001] プロジェクト初期設定・パッケージインストール（優先度: Must Have）
- [ ] [SETUP-002] DBスキーマ設計・ER図作成（優先度: Must Have）

### フェーズ2: インフラ・基盤
- [ ] [INFRA-001] usersテーブルのマイグレーションを作成する（優先度: Must Have）

### フェーズ3: ドメイン層
- [ ] [FR-001-01] User エンティティを実装する（優先度: Must Have）
- [ ] [FR-001-02] Email 値オブジェクトを実装する（優先度: Must Have）

...（省略）

合計: N タスク（Must Have: N / Should Have: N / Could Have: N）

このタスクリストで `tasks/todo.md` を作成し、TodoWrite にセットしてよいですか？
除外・追加・修正があれば教えてください。
```

修正があれば反映してからStep 5へ進む。

---

### Step 5: tasks/todo.md の作成・更新

`tasks/` ディレクトリが存在しない場合はBashで作成する。
`tasks/todo.md` が既に存在する場合は Read で内容を確認し、以下を AskUserQuestion で確認する：

- **上書き**: 既存の内容を置き換える
- **追記**: 既存の内容の末尾にフェーズ/セクションを追加する

以下のフォーマットで Write または Edit する：

```markdown
# タスクリスト: <プロジェクト/機能名>

作成日: YYYY-MM-DD
元要件: <要件ドキュメントのパス>
ステータス: In Progress

---

## フェーズ1: 設計・準備

- [ ] [SETUP-001] プロジェクト初期設定・パッケージインストール
  - 優先度: Must Have
  - 関連要件: -
  - 完了基準: ローカルで `npm run dev` が起動する

- [ ] [SETUP-002] DBスキーマ設計・ER図作成
  - 優先度: Must Have
  - 関連要件: FR-001, FR-002
  - 完了基準: ERDレビュー済み、マイグレーション設計が確定している

---

## フェーズ2: インフラ・基盤

- [ ] [INFRA-001] usersテーブルのマイグレーションを作成する
  - 優先度: Must Have
  - 関連要件: FR-001
  - 完了基準: マイグレーション実行後、テーブルが正しく作成される

---

## フェーズ3: ドメイン層

- [ ] [FR-001-01] User エンティティを実装する
  - 優先度: Must Have
  - 関連要件: FR-001
  - 完了基準: ユニットテストが全件パス

...

---

## 進捗サマリー

| フェーズ | 完了 | 総数 |
|----------|------|------|
| フェーズ1: 設計・準備 | 0 | N |
| フェーズ2: インフラ・基盤 | 0 | N |
| フェーズ3: ドメイン層 | 0 | N |
| フェーズ4: アプリケーション層 | 0 | N |
| フェーズ5: プレゼンテーション層 | 0 | N |
| フェーズ6: フロントエンド | 0 | N |
| フェーズ7: テスト | 0 | N |
| フェーズ8: 非機能要件対応 | 0 | N |
| **合計** | **0** | **N** |
```

---

### Step 6: TodoWrite へのセット

Must Have のタスクを優先し、フェーズ順に TodoWrite へ登録する。
Should Have / Could Have のタスクは `tasks/todo.md` には記録するが、TodoWrite へは登録しない（セッション内で注目するタスクを絞るため）。

TodoWrite のステータスは全タスク `pending` でセットする。

---

### Step 7: 完了報告

```
## タスク生成完了

| 項目 | 内容 |
|------|------|
| 元要件 | <ファイルパス> |
| 出力先 | tasks/todo.md |
| 総タスク数 | N |
| Must Have | N タスク（TodoWrite にセット済み）|
| Should Have | N タスク（tasks/todo.md のみ）|
| Could Have | N タスク（tasks/todo.md のみ）|

## 次のステップ（推奨）

- フェーズ1から順に着手する
- タスク完了時は `tasks/todo.md` の `[ ]` を `[x]` に更新する
- セッション開始時に `tasks/todo.md` を Read して進捗を把握する
```

---

## 注意事項

- タスクは **実装レベル（1〜2時間で完了できる粒度）** に分解する
- 受け入れ基準（Given/When/Then）がある場合は「完了基準」に反映する
- Must Have 要件のタスクを Should Have / Could Have より必ず先にフェーズ内で並べる
- 設計・インフラタスクは機能要件タスクより先のフェーズに置く（依存関係を守る）
- 要件ドキュメントが存在しない場合は推測でタスクを作らず、先に `/requirements` を実行するよう促す
- `tasks/todo.md` が既に存在する場合は必ずユーザーに上書き/追記を確認してから書き込む
- TodoWrite に登録するのは Must Have タスクのみとし、セッション内の焦点を絞る
