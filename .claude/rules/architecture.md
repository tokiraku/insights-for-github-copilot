# アプリケーションアーキテクチャルール

## 基本方針

- **フロントエンド・バックエンド分離型**を原則とする
- フロントとバックは**REST API または GraphQL**を介して通信する
- 双方は独立してデプロイ・スケール可能な構成にする
- **DDD（ドメイン駆動設計）の考え方**を導入し、役割と責務を明確にする

---

## フロントエンドの責務

- UIの描画・ユーザーインタラクションの処理のみを担う
- ビジネスロジックはフロントに持たない（表示ロジックは許容）
- バックエンドAPIを呼び出し、レスポンスを表示する
- 状態管理はUIの状態に限定する（ドメイン状態はサーバーが持つ）

---

## バックエンドの責務

- ビジネスロジック・ドメインルールはバックエンドに集約する
- 永続化・認証・認可・外部サービス連携を担う
- APIはリソース指向またはユースケース指向で設計する
- フロントエンドの都合に引きずられた実装を避ける

---

## フロントエンドのコンポーネント設計（アトミックデザイン）

フロントエンドのUIコンポーネントは**アトミックデザイン**で構成する。

```
atoms/       ← ボタン・入力欄・ラベルなど最小単位のUI部品
molecules/   ← atomsを組み合わせた小さなUIグループ（検索フォーム等）
organisms/   ← moleculesを組み合わせたページの構成要素（ヘッダー・カード等）
templates/   ← ページのレイアウト骨格（データは持たない）
pages/       ← templatesにデータを流し込んだ実際のページ
```

### 各レベルのルール

- **atoms**: 外部依存を持たない。スタイルと最小限のpropsのみ
- **molecules**: atomsのみに依存する。単一の機能を持つ
- **organisms**: atoms/moleculesに依存する。ビジネスロジックは持たない
- **templates**: レイアウトのみを担う。データフェッチ・状態管理を持たない
- **pages**: データフェッチ・状態管理はここで行い、templatesに渡す

---

## バックエンドのDDDレイヤー構成

バックエンドは以下の4層で構成する。層間の依存は**内側方向のみ**とする。

```
presentation/   ← HTTP ハンドラ・コントローラ・バリデーション
application/    ← ユースケース・アプリケーションサービス・DTOの組み立て
domain/         ← エンティティ・値オブジェクト・ドメインサービス・リポジトリインターフェース
infrastructure/ ← DB実装・外部API・リポジトリ実装
```

### 各層のルール

**presentation（プレゼンテーション層）**
- リクエストの受付とレスポンスの返却のみを担う
- バリデーションはこの層で行う
- ドメインオブジェクトをそのまま返却しない（DTO/レスポンスモデルに変換する）

**application（アプリケーション層）**
- ユースケース単位でクラス/関数を定義する（例: `CreateOrderUseCase`）
- トランザクション境界はこの層で管理する
- ドメインロジックをここに書かない（domain層に委ねる）

**domain（ドメイン層）**
- ビジネスルールをこの層に集中させる
- フレームワーク・DBへの依存を持たない
- リポジトリはインターフェースのみ定義し、実装は infrastructure 層に置く
- 値オブジェクトで不変条件を表現する（例: `Email`, `Money`）

**infrastructure（インフラストラクチャ層）**
- domain層のリポジトリインターフェースを実装する
- ORM・HTTPクライアント・メッセージキューなどの具体実装を置く
- 他の層がこの層に依存してはいけない（依存は逆転させる）

## ディレクトリ構成（例）

```
src/
  frontend/           ← フロントエンドアプリ（アトミックデザイン）
    components/
      atoms/          ← 最小単位のUI部品
      molecules/      ← atomsを組み合わせた小さなUIグループ
      organisms/      ← ページの構成要素
      templates/      ← レイアウト骨格
    pages/            ← データを流し込んだ実際のページ
    services/         ← APIクライアント
  backend/            ← バックエンドアプリ（DDDレイヤー）
    presentation/
    application/
    domain/
      model/          ← エンティティ・値オブジェクト
      repository/     ← リポジトリインターフェース
      service/        ← ドメインサービス
    infrastructure/
      persistence/    ← リポジトリ実装（DB）
      external/       ← 外部API実装
```

## API設計

- エンドポイントはリソースまたはユースケースを表す名詞で命名する
- レスポンスは統一フォーマット（`data`, `error`, `meta`）を使う
- 認証が必要な場合はステートレスなトークン方式（JWT等）を原則とする

---

## ローカル開発環境

- **Dockerコンテナを使用する**: ローカル開発環境はDockerコンテナで構築する
- **docker-compose を使う**: フロントエンド・バックエンド・DB等の依存サービスは `docker-compose.yml` で定義し、`docker compose up` 一発で起動できる状態にする
- **ホットリロード対応**: 開発時のDXを損なわないよう、ソースコードはボリュームマウントしてコンテナ内でホットリロードできるようにする
- **環境変数は `.env` ファイルで管理する**: `.env.example` をリポジトリに含め、`.env` は `.gitignore` に追加する
- **本番環境との差異を最小化する**: ローカルで使うDockerイメージは本番と同じベースイメージを使い、環境依存の不具合を防ぐ

---

## 禁止事項

- フロントエンドに直接DBアクセスさせない
- presentation層からdomain層・infrastructure層を直接呼び出さない
- domain層にフレームワーク固有のコードを混入させない
- 1つのユースケースに複数の責務を持たせない
