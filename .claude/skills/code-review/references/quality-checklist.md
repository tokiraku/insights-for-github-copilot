# 品質・可読性チェックリスト

## 命名規則

- [ ] 変数・関数・クラスの名前は意図を明確に表しているか
- [ ] 省略形や意味不明な1文字変数を使っていないか（ループカウンタの `i` 等は許容）
- [ ] 命名が言語/フレームワークの慣習に従っているか
- [ ] ブール値は `is`, `has`, `can`, `should` などのプレフィックスを使っているか

## 関数・メソッド

- [ ] 1関数が1つの責任のみ持っているか（単一責任の原則）
- [ ] 引数の数は適切か（目安: 3〜4個まで。それ以上はオブジェクト化を検討）
- [ ] 関数の長さは適切か（目安: 50行以内。超える場合は分割を検討）
- [ ] 副作用が明示的か（純粋関数が望ましい）
- [ ] 早期リターン（ガード節）を使って深いネストを避けているか

## 重複と再利用

- [ ] DRY原則に違反していないか（同じロジックが複数箇所にある）
- [ ] マジックナンバー・マジック文字列を定数化しているか
- [ ] コピーペーストしたコードが適切に抽象化されているか

## 可読性

- [ ] ネストが3レベル以内か
- [ ] 長い条件式を名前付き変数や関数に抽出しているか
- [ ] 三項演算子のネストなど可読性を下げるイディオムを避けているか
- [ ] コードの流れが上から下に読めるか（関数定義の順序）

## コメント・ドキュメント

- [ ] 「何をしているか」ではなく「なぜそうしているか」がコメントにあるか
- [ ] 古い/誤ったコメントが残っていないか
- [ ] 複雑なアルゴリズムや非自明なロジックに説明があるか
- [ ] TODO/FIXME が放置されていないか

## エラーハンドリング

- [ ] エラーを無視していないか（空の catch ブロック等）
- [ ] エラーメッセージは診断に十分な情報を含んでいるか
- [ ] 例外を適切な粒度でキャッチしているか（`Exception` など広すぎるキャッチに注意）
- [ ] ユーザー向けのエラーメッセージと内部ログを分けているか

## テスタビリティ

- [ ] 外部依存（DB・API・ファイルシステム）が抽象化されているか
- [ ] グローバル状態への依存を避けているか
- [ ] テストコードが存在するか（またはテスト可能な構造か）
