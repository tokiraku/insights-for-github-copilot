# タスク実装スキル

## 概要

`tasks/todo.md` のタスクリストをもとに開発を進める。
タスクの選択 → 要件確認 → 実装 → セルフレビュー → 進捗更新 の流れを一貫して実行する。

---

## 実行手順

### Step 1: タスクリストの読み込み

`tasks/todo.md` を Read で読み込む。
存在しない場合は「タスクリストが見つかりません。`/create-tasks` を先に実行してください」と出力して終了する。

---

### Step 2: 対象タスクの特定

#### 現在フェーズの特定

タスクを選択する前に「現在フェーズ」を特定する。
**現在フェーズ** = 未完了タスクが存在する最も若い番号のフェーズ。

#### 引数が渡された場合

- `next` が指定された場合: 現在フェーズ内で優先度順（Must Have → Should Have）の最初の未完了タスクを自動選択する。現在フェーズ内に未完了タスクがなければ「フェーズ完了」として Step 2a へ進む
- タスクID（例: `FR-001-01`）が指定された場合: そのタスクを対象にする
- タスクIDが見つからない場合はエラーを出して一覧を提示する

#### 引数が省略された場合

**現在フェーズ内**の未完了タスクを以下の形式で一覧表示し、AskUserQuestion でどれを実装するか確認する。

```
## 未完了タスク一覧（フェーズN: フェーズ名）

- [ ] [SETUP-001] プロジェクト初期設定（Must Have）
- [ ] [SETUP-002] DBスキーマ設計・ER図作成（Must Have）

どのタスクを実装しますか？タスクIDを入力してください（例: SETUP-001）
または "next" で優先度順の最初のタスクを自動選択します。
```

#### Step 2a: フェーズ完了時の確認

現在フェーズの全タスクが完了している場合、以下を表示して AskUserQuestion で確認する。

```
## フェーズN: フェーズ名 — 完了

フェーズN のすべてのタスクが完了しました。
次のフェーズ（フェーズN+1: フェーズ名）に進みますか？

- はい → 次のフェーズのブランチを新規作成して実装を開始します
- いいえ → 現フェーズのブランチで PR 作成を推奨します（`/github-create-pr`）
```

「はい」の場合は次のフェーズを現在フェーズとして Step 3 に進む。
「いいえ」の場合は処理を終了する。

---

### Step 3: タスク詳細と要件の確認

対象タスクの詳細を `tasks/todo.md` から抽出する：

- タスクID・タスク名
- 優先度
- 関連要件ID（FR-xxx / NFR-xxx など）
- 完了基準

#### 要件ドキュメントの参照（必須）

`docs/requirements/` 配下のファイルをすべて Read する。存在しない場合はスキップしてよい。

確認する内容：

| ファイルパターン | 確認内容 |
|----------------|---------|
| `*-tech-requirements.md` | 技術スタック・非機能要件・技術制約・アーキテクチャ概要 |
| その他 `*.md` | 機能要件（FR-xxx）の受け入れ基準（Given/When/Then） |

ファイルが多い場合は、対象タスクの関連要件ID（FR-xxx / NFR-xxx）に対応するセクションを優先して読む。

技術スタック・アーキテクチャルールが不明な場合は `.claude/rules/` 配下のルールファイルを読む。

---

### Step 4: 実装計画の提示・承認

実装方針をユーザーに提示してから着手する。

```
## 実装計画: [タスクID] タスク名

### 対象タスク
- **タスクID**: タスクID
- **完了基準**: 〇〇が満たされていること
- **関連要件**: FR-001（ユーザー登録機能）

### 実装方針
1. 〇〇を作成する（ファイルパス）
2. 〇〇に〇〇を追加する（ファイルパス:行番号）
3. ユニットテストを作成する（ファイルパス）

### 影響範囲
- 新規ファイル: N個
- 変更ファイル: N個

この計画で実装を開始してよいですか？
```

ユーザーの承認を得てから Step 5 に進む。
修正があれば計画を更新して再提示する。

---

### Step 5: ブランチ確認・作成

**1フェーズ = 1ブランチ**を原則とする。

#### 既存ブランチの確認

現在のブランチを `git branch --show-current` で確認する。
現在のブランチが当該フェーズのブランチ（命名規則に合致するもの）であれば、ブランチ作成をスキップして Step 6 に進む。

#### 新規ブランチが必要な場合（フェーズ開始時のみ）

##### ブランチ名の規則

```
<type>/phase<N>-<phase-short-name>
```

- `<type>`: フェーズの主な内容に応じて以下から選ぶ
  - `feat` — 機能実装フェーズ（ドメイン層・アプリ層・プレゼンテーション層・フロントエンド）
  - `chore` — 設計・準備・インフラ・環境構築フェーズ
  - `test` — テスト専用フェーズ
  - `refactor` — リファクタリング専用フェーズ
- `<N>`: フェーズ番号（例: `3`）
- `<phase-short-name>`: フェーズ名を短く英語にしたもの（ケバブケース）

例:
- `chore/phase1-setup`
- `chore/phase2-infrastructure`
- `feat/phase3-domain-layer`
- `feat/phase4-application-layer`
- `feat/phase5-presentation-layer`
- `test/phase7-testing`

##### 実行手順

1. `develop` ブランチに切り替える
   ```bash
   git checkout develop
   ```
2. 最新の `develop` を取得する
   ```bash
   git pull origin develop
   ```
3. 作業ブランチを作成して切り替える
   ```bash
   git checkout -b <branch-name>
   ```

ブランチ作成後、ブランチ名をユーザーに報告してから Step 6 に進む。

---

### Step 6: 実装

承認された計画に従って実装する。

#### 実装時のルール

- **アーキテクチャルール準拠**: `.claude/rules/architecture.md` のDDDレイヤー構成に従う
- **コードスタイル準拠**: `.claude/rules/code-style.md` の命名規則・フォーマットに従う
- **セキュリティルール準拠**: `.claude/rules/security.md` の禁止事項を守る
- **1タスク = 1コミット単位**: タスクの粒度で完結する実装にする
- **テストを同時に書く**: ドメイン層はユニットテスト、インフラ層は統合テストを必須とする（`.claude/rules/testing.md` 参照）

#### 既存コードがある場合

- 変更対象ファイルを必ず Read してから Edit する
- 既存の命名規則・パターンに合わせる
- 既存テストが壊れないよう確認する

#### 実装中の報告

各ファイル作成・編集後に「✓ `ファイルパス` を作成/更新しました」と短く報告する。

---

### Step 7: セルフレビュー

実装完了後、以下の観点でセルフチェックを行う。

| チェック項目 | 確認内容 |
|------------|---------|
| **完了基準の充足** | `tasks/todo.md` の完了基準をすべて満たしているか |
| **受け入れ基準の充足** | Given/When/Then がすべて満たされているか |
| **技術要件との整合** | 技術スタック・非機能要件・技術制約（`*-tech-requirements.md`）に違反していないか |
| **アーキテクチャ準拠** | レイヤー間の依存方向が正しいか |
| **テスト網羅** | ハッピーパス・エラーパス・エッジケースが揃っているか |
| **セキュリティ** | 外部入力のバリデーション・シークレットのハードコードがないか |
| **未使用コード** | 未使用のインポート・変数がないか |

問題が見つかった場合はその場で修正する。

---

### Step 8: tasks/todo.md の進捗更新

セルフレビューが完了したら `tasks/todo.md` を更新する。

- 完了したタスクの `[ ]` を `[x]` に変更する
- 「進捗サマリー」テーブルの完了数をインクリメントする

```markdown
<!-- 変更前 -->
- [ ] [FR-001-01] User エンティティを実装する

<!-- 変更後 -->
- [x] [FR-001-01] User エンティティを実装する
```

---

### Step 9: 完了報告

#### タスク完了時（フェーズ内に未完了タスクが残っている場合）

```
## 実装完了: [タスクID] タスク名

### 実装内容
| ファイル | 操作 | 概要 |
|---------|------|------|
| `path/to/file.ts` | 新規作成 | User エンティティクラス |
| `path/to/file.test.ts` | 新規作成 | User エンティティのユニットテスト |

### 完了基準の確認
- [x] 〇〇が実装されている
- [x] ユニットテストが全件パス

### 作業ブランチ
- ブランチ: `<branch-name>`

### フェーズ進捗
- フェーズN: X / Y タスク完了

### 次のアクション（推奨）
- コミット・プッシュ: `/github-commit-push`
- コードレビュー: `/code-review <実装ファイルパス>`
- 同フェーズの次のタスクへ: `/implement-task next`
```

#### フェーズ完了時（フェーズ内の全タスクが完了した場合）

```
## フェーズ完了: フェーズN — フェーズ名

### 実装内容
| ファイル | 操作 | 概要 |
|---------|------|------|
| `path/to/file.ts` | 新規作成 | ... |

### 完了基準の確認
- [x] 〇〇が実装されている
- [x] ユニットテストが全件パス

### 作業ブランチ
- ブランチ: `<branch-name>`

### フェーズ進捗
- フェーズN: Y / Y タスク完了 ✓

### 次のアクション（推奨）
- コミット・プッシュ: `/github-commit-push`
- PR を作成して develop にマージ: `/github-create-pr`
- 次のフェーズへ: `/implement-task next`（マージ後に実行）
```

---

## 注意事項

- **1フェーズ = 1ブランチ** — フェーズ内のタスクはすべて同じブランチで実装する
- **実装は必ず専用の作業ブランチで行う** — `develop` や `main` に直接コミットしない
- **フェーズをまたいで実装しない** — 現在フェーズが完了するまで次のフェーズのブランチを作成しない
- **実装前に必ず計画を提示してユーザーの承認を得る** — 無断で実装を開始しない
- 要件ドキュメント・アーキテクチャルールが存在する場合は必ず参照してから実装する
- 完了基準が曖昧なタスクは着手前に AskUserQuestion で確認する
- テストが走る環境（`npm test` / `pytest` 等）がある場合はテストを実行して結果を確認する
- 実装が予想より大きくなる場合は、タスクをさらに分割してユーザーに確認する
- `tasks/todo.md` の更新は実装完了・確認済みの後に行う（途中状態で更新しない）
- セルフレビューで問題が見つかった場合は、ユーザーに報告してから修正する
